# コトホグ セリフCMS（ローカル専用）

外部サービスやDBは不要。Python標準ライブラリだけで動く、ブラウザ用の編集画面です。

## 起動する

PowerShell でリポジトリのルートから:

```powershell
cd C:\Users\mail\work\kotohogu
python tools/dialogue_cms/server.py
```

ブラウザで **http://127.0.0.1:8765** を開く。終了はターミナルで Ctrl+C。

## できること

- キャラIDと画像フォルダ名は全キャラで一致します。うさぎは `002_usagi`、しばいぬは `001_shiba` です。PNGは `assets/characters/<キャラID>/` に置きます。旧6キャラのIDを整理したため、旧IDを含む開発用セーブは端末データを初期化してから使ってください。
- キャラ管理画面で、各住民のプロフィール（自由文1項目、改行可、最大1000文字）と「桜の美容室の住民かどうか」を編集・保存。一般の住民は出現エリアを指定せず、開放済みエリアへランダムにお出かけ。美容室には最大7人まで所属できます。つやこさん（035_beaty）は美容室のオーナーでガチャ対象・屋外非表示の固定設定です。つやこさんをガチャでお迎えすると美容室が開放されます。きものぎつねもガチャ対象ですが、この子だけでは開放されません
- キャラ一覧の「選択キャラを削除」で登録済み住民を削除済みに移し、「削除済み・復元する」から戻せます。保存済みの所持を読み込めるよう、定義・画像・セリフは物理削除しません。削除済みの子は通常CMS一覧・新規ガチャ（1回・11回）・まち・拍手・リモートプレビューから除外します。初期住民・コード参照による削除禁止はサーバーの判定を画面に表示し、削除前に止めます。セリフ条件の未保存の変更も確認します。保存前に新規追加した子は「追加を取り消す」で除去します
- キャラ別のセリフを追加・修正・削除（セリフIDはキャラID＋連番で自動発行。会話・豆知識の区別なし）
- キャラ設定とセリフ編集では、選択中のキャラの正面待機画像（`assets/characters/<画像フォルダ>/idle_front_01.png`）を1枚だけ表示します。画像がない場合はエラー表示し、他の画像への切り替えは行いません。
- 累計ミッション回数（合計・種類別）と「達成当日だけ表示」（1日固定）の組み合わせ、ことほぎによる表示条件
- 指定日・指定期間・毎年の指定日・毎年の期間・曜日による表示条件
- 条件の AND / OR、優先順位、初回のみのセリフ
- まちに2人のキャラが実際に表示されているときだけ成立する条件と、相手の返事（掛け合い）
- 特定の住民を「所持している／していない」条件（例：つやこさんのお迎え前後で案内係の噂を切り替える）。プレビューでは仮の所持チェックで確認でき、まちに同時表示されているかとは独立です
- 「特定のセリフIDを見たことがある」条件。全キャラ共通なので、別のキャラの会話を続きの条件にできます
- 仮の日付・ミッション実績によるセリフ表示プレビュー
- JSON スキーマ検証後、`assets/dialogues/dialogues.json` を安全に上書き

**保存後、公開済みのアプリが即時更新されるわけではありません。** JSONをGitにコミットし、Flutterアプリを再ビルドして反映してください。

```powershell
git status
git add assets/dialogues/dialogues.json assets/characters/characters.json
git commit -m "Update dialogue content and sequence counters"
git push
```

## 累計カウントと古いセーブについて

アプリ内部の保存形式はv5。従来v4から明示的に移行し、過去の履歴に残っている種類別ミッション回数のみを初期カウントとして復元します。すでに削除された履歴、同日デバッグ再達成など不明な過去の回数は作りません。新しい達成は累計カウントへ加算され、履歴を削除しても減りません。全ミッション累計だけは既存の「ことほぎ ÷ 10」で確定できます。

## 条件仕様

```json
{
  "id": "shiba_sakura_outside_5",
  "residentId": "001_shiba",
  "text": "桜の季節だね！最近のお散歩はどうだった？",
  "priority": 20,
  "once": false,
  "logic": "all",
  "conditions": [
    { "type": "date", "mode": "annual_range", "start": "03-20", "end": "04-10" },
    { "type": "mission", "missionId": "outside", "minCount": 5 }
  ]
}
```

ミッション条件の「達成当日のみ表示」をONにすると、`"withinDays": 1` が追加されます。この条件は日本時間の達成当日だけ成立し、日数は変更できません（2以上の設定は保存・読み込み時に拒否します）。累計回数を満たし、かつ当日に同じ種類の達成履歴が残っている場合だけ有効です。履歴を削除した場合は累計から当日の達成を推測しません。CMSプレビューでは仮の達成日とミッション種類を指定できます。`once=true` と組み合わせると、その日を含め一度だけ登場します。既存の `withinDays` のない条件は累計判定のままです。

日本時間（JST）で日付を判定します。指定期間の両端を含めます。毎年の期間は12月〜1月の年越しも扱えます。閏日の年次セリフは2月29日がある年のみ表示します。曜日は月曜=1〜日曜=7です。

セリフに種類の区別はありません。条件を満たす未読の `once=true` セリフがあれば、その中で最優先のものを表示（同順位は抽選）。ない場合は、繰り返し可能な全候補を `1 + max(0, priority) ~/ 10` の重みで確率抽選します。優先順位0も候補で、同じセリフの連続も許可します。優先順位 `-1000` の施設専用セリフは通常抽選から除外し、施設側がIDを指定して選びます。条件が無い、かつ `once=false` の通常セリフを各キャラ最低1件要求します。条件に合わない時は通常セリフに戻ります。**すべてのセリフ**について初回表示時にIDを閲覧済みとして保存します。`once=true` の行だけは、そのIDが閲覧済みになると以後の候補から外れます。

CMSの条件プレビューでは「見たことがあるセリフ（仮設定）」から既読IDを選択できます。実際のセーブデータは変更しません。

## 別キャラにも使える既読セリフID条件

セリフCMSの表示条件に「指定セリフを見たことがある」を追加して、全キャラのセリフIDから選択します。
セリフの種類やキャラID、2人の組み合わせに依存しない共通条件です。

```json
{
  "id": "003_penguin_001",
  "residentId": "003_penguin",
  "text": "さっきのお話の続き、聞かせてね",
  "priority": 20,
  "once": false,
  "logic": "all",
  "conditions": [
    {"type": "seenDialogue", "dialogueId": "009_chef_002"},
    {"type": "townTogether", "otherResidentId": "004_neko"}
  ],
  "reply": {"residentId": "004_neko", "text": "わたしも聞きたい！"}
}
```

この例はシェフの `009_chef_002` を見たことがあり、かつペンギンとねこが
まちにそろっているときだけ、2人の会話を表示します。セリフIDは全キャラを通じて一意です。
参照するセリフIDが存在しない・自分自身である場合は保存エラー。
参照先のセリフを削除する場合は、まず依存する条件を外す必要があります。
以前のセーブデータに既読記録がない通常セリフは、更新後に改めて表示されると記録されます。
セーブ形式（v5）およびセリフJSONの版（v1）は変更しません。

## まちで2人そろったときの特別な掛け合い

セリフCMSで発言するキャラを選び、表示条件に
「まちで2人そろう」を追加して、一緒にいる**相手キャラ**を選びます。
条件の組み合わせは AND にして、必要なら「＋ 相手の返事を追加」で
そのキャラの返事も入力します。相手がいなければこの掛け合いは出ません。

```json
{
  "id": "001_shiba_001",
  "residentId": "001_shiba",
  "text": "今日は雲をながめようよ",
  "priority": 20,
  "once": false,
  "logic": "all",
  "conditions": [
    {"type": "townTogether", "otherResidentId": "002_usagi"}
  ],
  "reply": {"residentId": "002_usagi", "text": "あの雲、絵に描きたい！"}
}
```

通常の1人のセリフは `reply` なしで従来通り。返事は省略可能です。
`reply` を付けるなら、AND条件の「まちで2人そろう」で指定した相手だけが
返事を話せます。違う人が返事をする定義は保存時に拒否します。
ゲーム内の判定は「所持している2人」だけではなく、ガチャの所持順から
「まちに表示」ONの住民を最大8人選んだ**実際の表示枠**に2人とも入ること。
ホームに並ぶキャラとまちの表示枠は同じ基準です。
CMSのプレビューではチェックした仮のまち住民を使って確認できます。
既存のセリフID・保存データ・通常会話と豆知識を分けない設計は変わりません。

## セリフIDの自動採番

セリフ管理タブで「キャラクターで絞る」から追加先を選び、「＋ セリフ追加」を押すと
`キャラID_連番` を自動発行します（例: `009_chef_001`, `009_chef_002`）。
番号は各キャラで独立しており、最低3桁のゼロ埋めです（1000件目は4桁）。
セリフID・所属キャラはセーブデータと閲覧済み記録の参照に使うため変更不可。
既存の `shiba_default_1` などの旧IDは変更せずに残します。

登録済みキャラの `nextDialogueNumber` は `assets/characters/characters.json` に
保存し、削除したセリフの番号も再利用しません。キャラの名前や、日付・ミッション条件、
セリフ本文、優先順位などは通常どおり編集できます。
CMS保存時はIDと連番が整合するか検証し、食い違いがあれば保存しません。


## 安全性

サーバーは `127.0.0.1` のみに待ち受け、PUTを同一オリジンに制限します。データはJSON検証後に一時ファイルへ書き、原子的に差し替えます。GitHubへの変更はCMSが自動では実行しません。

検証: `python -m unittest discover -s tools/dialogue_cms -p 'test_*.py'`


## 🌸 初対面のあいさつ

キャラ管理タブの「🌸 初対面のあいさつ（1回のみ）」から、その子に初めて話しかけた際の自己紹介を編集できます。同じ画面の「＋ 初対面のあいさつを登録」で付けられます（任意）。

登録中のあいさつ本文は必須・500文字以内です。空欄や空白だけの場合、キャラ名とセリフIDを表示して保存前に停止します。名前・プロフィールなど編集中の変更は保持し、空の本文を自動で書き換えたり、あいさつを自動削除したりしません。プロフィールは空欄でも保存できます。

あいさつを使わない場合は「初対面のあいさつを削除」を押し、確認後に保存してください。通常セリフは保持します。このあいさつを既読条件に使うセリフがある場合は、その参照を先に外す必要があります。削除した連番は再利用しません。

内部的には、通常の `dialogues.json` エントリーに `"firstGreeting": true` を付けます。**未読であれば最優先**し、ミッション達成・初回限定の物語・通常の確率抽選より必ず先に表示します。既読になれば候補から消え、次回から従来の優先度／重み付き抽選です。同じ住民に初対面セリフを複数登録できません。初対面の条件・複数話者・通常の優先順位は設定できず、`once=true`／条件なしで固定です。

旧版から更新した既存ユーザーは、これまでの会話を閲覧済みでも **今回追加した初対面IDだけは未読**なので、アップデート後にその住民へ最初に話しかけたときに一度だけ表示されます。既存の既読履歴・セーブ形式は変更しません。施設で話しかける場合も、通常の住民会話ではこの条件を使いますが、マルシェの専用カウンター会話は別途ID指定で選びます。

## エリア・住民出現場所の管理

CMSの **「🗺️ エリア管理」** タブでは、4つの屋外エリアの名称・説明・開放に必要な累計ことほぎを編集できます。背景画像は読み取り専用でプレビューし、アセットのパス・画像サイズ・エリアID・順序は変更しません。

エリアは `assets/town/areas.json`（version 1）を正本とし、保存時に `lib/town_areas.dart` の `BEGIN/END CMS TOWN AREAS` 間へ自動生成します。これによりアプリのエリア開放判定にも反映されます。中央ひろばは0ことほぎ、以後の開放値はエリア順に増加するようにしてください。

通常の屋外住民に出現エリア設定はありません。まちを開いたとき、実際に開放されているエリアから等確率で1か所を抽選し、その滞在中は行き先を保ちます。キャラ管理には、特別な「桜の美容室の住民（室内だけ）」だけをチェック項目として残します。つやこさんの所属は固定、美容室は最大7人です。従来の `homeAreaId` は既存のキャラJSON／Flutter enum／デバッグ画面との互換性のため保持しますが、通常の屋外出現先には利用しません。屋外の値は旧データのまま保持し、新キャラは互換値 `plaza` を自動登録します。

**出現プレビュー** では仮の累計ことほぎとマルシェ開店状態を指定し、全員を取得済みと仮定したお出かけ先を見られます。選択中のエリアへの来訪者を先に表示し、ほかのエリアの結果は折りたたみで確認できます。居住地一覧や住まい別フィルターはありません。開放済みエリアから住民ごとに1か所を抽選し、「お出かけ先を決め直す」までは保持します。開放エリアの数を変えると新しい配置例を作ります。とんこは開店後に中央ひろばで店番、美容室の住民は室内のままです。プレビューは実際の所持データや既読履歴を書き換えません。

これらの特別な配置条件・固定位置・時間帯による出現・背景の自動切り替えは、**まだCMSからは編集できません**。表示上の説明と仮プレビューのみで、既存の `lib/town_areas.dart`・`lib/marche.dart`・`lib/town.dart` の判定はそのまま残します。

保存は従来の `/api/cms` から行い、キャラ・セリフ・エリアJSONと生成Dartを検証後にまとめて差し替えます。従来の `characters` / `dialogues` だけの保存リクエストにも対応し、エリア設定を保持します。公開反映にはGitコミットと再ビルドが必要です。

追加ファイル: `assets/town/areas.json`、`tools/dialogue_cms/areas.py`、`tools/dialogue_cms/test_areas.py`。

## キャラクター登録（CMS）

管理画面の「キャラクター管理」で「＋ キャラ追加」を押します。先に
`assets/characters/<キャラID>/` へスプライトを配置し、
名前・プロフィール・美容室への所属（必要な子だけ）・安定したキャラID（例: `009_chef`）・ガチャ登場・屋外に登場するかを指定します。
新規キャラは画像フォルダをIDと同じ名前にし、Dart識別子は `c` + ID（例: `c009_chef`）で自動生成します。
IDは数字2桁以上とアンダースコア・英小文字の名前で構成します。
セリフ管理タブには、そのキャラの `キャラID_001` という条件なしセリフが自動追加されています。会話も豆知識も同じセリフ欄から登録し、必要な条件を付けてください。

各フォルダには `idle_front_01.png`、`clap_front_01.png` と
`clap_front_02.png`、上下左右それぞれ `walk_<方向>_01.png`〜
`walk_<方向>_04.png` が必要です（元から存在するしばいぬのみ左向きを右画像反転で代用）。
例: `assets/characters/009_chef/`。フォルダがない場合や画像不足は保存エラーとなります。

キャラ設定に「Tipsの元キャラ」はありません。すべてのセリフは `assets/dialogues/dialogues.json` だけで管理します（セリフJSONは引き続きversion 1）。
キャラ定義JSONはプロフィール `profile`（最大1000文字の文字列、空欄可）を含むversion 4です。既存の登録住民は空文字で明示的に移行済みです。既存のID・採番カウンターはそのままです。

保存は `assets/characters/characters.json` と
`assets/dialogues/dialogues.json` に加えて、
`lib/resident_collection.dart` のCMS生成領域（`TownResident.profile` も使用可能）と
`pubspec.yaml` のキャラアセット登録領域を同期します。
既存住民のID・内部識別子・画像フォルダは変更・削除できません（既存の異なる命名は維持します）。
所持済み住民を安全に保持するため、ガチャ対象外やまち非表示にするフラグを使用してください。
ガチャは「ガチャに登場」がONのキャラから等確率で選びます。
まちでは所持する屋外対象の住民を全員、それぞれ1か所へ配置します。ホームや拍手の表示人数とは別の規則です。

```powershell
python -m unittest discover -s tools/dialogue_cms -p 'test_*.py'
flutter analyze
flutter test
git status
git add assets/characters/characters.json assets/dialogues/dialogues.json lib/resident_collection.dart pubspec.yaml
git commit -m "Update residents with local CMS"
git push
```

CMSはローカル専用です。プロフィールも含め、保存してGitへ反映・アプリ再ビルドするまで公開アプリには反映されません。プロフィールのゲーム内表示画面は今回追加しません。
カタログversion 4への移行前に、未保存のセリフやキャラ設定は必ず別途バックアップしてください。旧CMSを開いたままの保存は行わず、`git pull --ff-only` とサーバー再起動、ブラウザ再読み込みを行ってください。

## ランダムなお出かけとまちの拡張

通常の住民のお出かけ先は、開放済みエリアからランダムに決めます。キャラCMSから「住むエリア」の編集を取り除きました。従来の `homeAreaId` は **version 5** のキャラ台帳とFlutterの互換性を維持するため残し、`salon` だけ屋内所属として扱います。進捗セーブの形式は変更しません。

エリア開放はミッションで得た累計ポイントで判定します（0 / 90 / 180 / 300）。ガチャで使えることほぎ残高とは別です。背景画像がまだないエリアは準備中画面に住民を表示し、別エリアの画像を流用しません。未開放エリアには通常は入れません。デバッグで住民を選択したときのみ、未開放エリアのプレビューが可能です。

「まちで2人そろう」条件は、同じエリアに実際に表示される住民だけで判定します。アプリはまちを開いたときの `TownVisit` を描画と条件判定で共有し、エリア移動や会話では再抽選しません。ホーム画面は従来どおり先頭8人を表示します。新背景の追加時は `lib/town_areas.dart` に背景アセットのパスを登録し、`pubspec.yaml` に追加してください。

## ローカル配信の検証（Androidエミュレーター）

FlutterでCMSの住民設定・セリフ・スプライトを、アプリ同梱アセットではなくHTTPから表示する検証用エントリーポイントを追加しました。**本編のガチャ・町・セーブデータはこの段階では従来どおりです。**

PowerShellの1つ目のターミナルでリポジトリを更新し、CMSを起動します。

```powershell
cd C:\Users\mail\work\kotohogu
git pull --ff-only origin main
python tools/dialogue_cms/server.py
```

別のターミナルで配信データを確認します。

```powershell
Invoke-RestMethod http://127.0.0.1:8765/api/runtime/catalog
```

Androidエミュレーターを起動して、Flutterのプレビューアプリを実行します。

```powershell
flutter run -t lib/local_content_preview.dart --dart-define=KOTOHOGU_LOCAL_CONTENT_URL=http://10.0.2.2:8765
```

Androidエミュレーターの `10.0.2.2` は、ホストPCの `127.0.0.1` を指します。**実機では使えません。** CMSは安全のためローカルループバックにのみ待ち受け、デバッグのAndroidアプリだけHTTPを許可します。Flutter Webはこのプレビュー対象外です。

プレビューで住民を選択すると正面・拍手・歩行のフレームとセリフを確認できます。CMSで新キャラを追加したら右上の更新ボタンで読み直せます。配信エラーや不正なJSON、画像の取得失敗は表示して止めます。暗黙のフォールバックはありません。

追加API: `GET /api/runtime/catalog`（検証済みの全キャラ＋セリフ）、`GET /api/runtime/sprites/<artFolder>/<filename>`（登録済みキャラの画像のみ）。編集用の既存APIやCMS画面は変更しません。

検証コマンド：

```powershell
python -m unittest discover -s tools/dialogue_cms -p 'test_*.py'
flutter test test/local_content_preview_test.dart
```

**次段階**：固定 `TownResident` enum を動的モデルに置換し、この配信データを通常のガチャ・町・会話画面へ取り込みます。これが完了するまでは通常アプリへ新キャラをコード更新なしで追加できるわけではありません。

## 本編のまちへのローカル配信テスト（Androidエミュレーター）

配信テスト用のURLを指定して、**通常のゲーム**を起動できます。CMSサーバーを立ち上げたまま、別ターミナルでFlutterを実行してください。

ターミナル1:
```powershell
cd C:\Users\mail\work\kotohogu
git pull --ff-only origin main
python tools/dialogue_cms/server.py
```

ターミナル2:
```powershell
cd C:\Users\mail\work\kotohogu
flutter run -t lib/main.dart --dart-define=KOTOHOGU_LOCAL_CONTENT_URL=http://10.0.2.2:8765
```

通常のまちには**ガチャで仲間にした子だけ**が表示されます。CMSに登録した未所持キャラは自動表示されません。開発中に確認したい場合はメニューの「未所持の配信住民をお試し表示」をONにすると、そのときだけ「配信テストの来訪者」として表示できます。アプリのenumにない新住民は全員がプレビュー対象で、既存住民は未所持かつ最近登録された最大2人をサンプル表示します。所持済み住民と重複せず、プレビューはアプリを終了するとOFFに戻ります。

CMSで新しい住民を保存したら、まち画面右下の再読み込みアイコンを押してください。新キャラの歩行画像をHTTPで表示します。画像不足や通信エラーでは別の画像へ自動切り替えしません。

- 来訪者はCMSの `walkInTown=true` のキャラだけです。美容室など歩かない設定のキャラは屋外へ出ません。
- **デバッグ表示をONにした場合だけ**、来訪者も開放済みエリアからランダムにお出かけします。まち滞在中は現在の行き先を保持し、新しい訪問で再抽選します。
- タップすると条件なし・繰り返し可能なセリフで会話します。条件付きセリフ・既読記録はこの段階では対象外です。
- 来訪者との会話や表示はローカルの所持データ・ガチャ・進捗セーブに書き込みません。
- 配信URLを指定しない通常起動の挙動は変更しません。URLを指定した場合、通信・検証失敗時はまち表示を止めます。
- Androidエミュレーターの `10.0.2.2` を使用します。物理端末・本番配信では使用しません。

確認用:
```powershell
python -m unittest discover -s tools/dialogue_cms -p "test_*.py"
flutter test test/local_content_preview_test.dart test/local_town_visitors_test.dart test/local_town_integration_test.dart
flutter analyze
```

本番用AWS配信には、ガチャ・所持データを含めた動的住民モデルへの移行、HTTPSでの配信、スナップショットのバージョン管理・署名/ハッシュ検証などを別途実装します。

このHTTP接続は **Flutterデバッグビルド専用** です。`KOTOHOGU_LOCAL_CONTENT_URL` を指定したリリースビルドでは起動時に明示的に停止します。


## ゆうぐれおやすみクラブ

管理画面上部の「イベント仕様・プレビュー」または `/events` を開きます。
- 保存元は `assets/events/oyasumi_club.json`。保存すると `lib/oyasumi_config.g.dart` も同時に生成されます。アプリへの反映には再ビルドが必要です。
- 開始・終了時刻、各段階の配置、導入文、繰り返し会話3〜4本、参加後の昼の会話を編集できます。
- プレビューで日時、所持状況、読了段階を指定し、「導入を最後まで読む」「次の夜へ」を試せます。実セーブは変更しません。判定には未保存の編集内容を使います。
- 開催は端末の現地時刻18時〜翌5時が初期値。5時前は前日の開催夜です。連続ログインは不要で、一度に一段階だけ進みます。
- おやすみくん未所持では非開催。かえる未所持では一人のクラブを継続します。かえるを入手し、一人の導入読了より後の開催夜に見学が始まります。
- 導入を最後まで読んだときだけ進行を保存します。閉じる・戻る・保存失敗では進みません。かえる参加後は通常の会社員会話を抽選せず、休養生活の会話を選びます。
- 「繰り返し会話」や「参加後のかえる：昼間・通常会話」では、各パターンの「次の発言を追加」から、住民を指定した複数ターンの掛け合いを編集できます。会話パターン3〜4本、1パターン最大8発言。既存の文字列だけのセリフはそのまま有効で、発言を追加したパターンだけ複数話者形式になります。
- 夜の掛け合いはその段階で広場に登場している住民だけ、参加後の昼の掛け合いは屋外住民と設定できます。昼間の掛け合いは、**話しかけた場所で相手が実際に同席しているときだけ**候補になり、不在なら一人用の会話から選びます。キャラ一覧から話しかけた場合も一人用のみです。昼間の一人用会話は最低1本必要です。
- CMSの「仮の状態で確認」には「昼間、かえると同じ場所にいる住民」欄があり、同席者ごとにどの掛け合いが候補になるか試せます。仮プレビューは保存データに影響しません。
- 夜の出演者は通常の散歩配置から除外し、ひろばへ一度だけ配置します。既存の所持状態は変更しません。

### 実装上の境界

`OyasumiProgress` は読了段階と最終開催日だけを保存します。`OyasumiScene` が背景・出演者・配置・会話グループをまとめて決定し、描画と `TownRules` が同じ判定を参照します。既存セーブでは未開始として読み込みます。
CMSの判定は `events.py`、アプリの判定は `oyasumi_club.dart` にあり、同じ仕様JSONを読みます。両方の段階判定テストを変更時に実行してください。
今後の夜限定の家などは、同じ時間帯の設定と物語の進行値を参照し、入口の可否と案内文を一か所で決める構成にします。現時点では家の開放機能は追加していません。

確認: `flutter test test/oyasumi_club_test.dart`、`python -X utf8 -m unittest discover -s tools/dialogue_cms -p test_events.py`。
